# Local files and memory

File answers use a dedicated evidence-only prompt, with numbered excerpts passed as user data instead of system instructions. File questions bypass normal chat's app-launch, identity and calculator shortcuts. Missing or out-of-range citation numbers trigger an extractive fallback showing the matching excerpts. This validates citation IDs, not whether every generated claim is semantically supported; verify the cited excerpts. Saved memory notes, when included in all-files mode, receive their own source entry.

PDF support: text-based `.pdf` files can be browsed, previewed, indexed and queried, using Apache PDFBox 3.0.8. Limits are 2 MB per file, 50 pages and 16 KB of extracted UTF-8 text. Encrypted, malformed and textless PDFs are rejected on direct read and skipped during folder indexing. OCR, images, attachments, scripts and visual layout are not processed. References use extracted-text lines rather than PDF page numbers. PDFs are read-only in JARVIS: edit the original externally, then reindex. Processing checks limit text positions and operators; a 15-second deadline is checked during content operators, but this is not a hard timeout or a memory sandbox for the parser. See [Apache PDFBox](https://pdfbox.apache.org/) for the extraction library.

Open **Files & memory** in JARVIS. Browse a drive or enter an absolute folder path, then choose **Index this folder**. Ask a question in **Ask your files** to retrieve matching lines and generate a local answer with source paths and line numbers. Normal chat also receives a short excerpt of your saved memory notes. File contents and memory are never sent to web search.

In **Ask your files**, choose **Search in** to restrict retrieval to one indexed file. Both keyword and vector searches filter to that file before ranking; saved memory notes are excluded for this selection. The default **All indexed files & memory** retains the existing behavior. A forgotten or unknown selection is rejected. API clients can send an optional `path` in `POST /api/v1/files/answer`, using an exact path returned by `/memory`; omit it or send `null` for all files. No database migration is required.

Vector indexing records the configured embedding model name and dimension count in each chunk's existing metadata. After changing `JARVIS_EMBEDDING_MODEL`, restart JARVIS and choose **Index this folder** again: unchanged files are re-embedded when their model metadata differs or is missing. Search excludes vectors from other models and legacy vectors without metadata until reindexed; keyword retrieval remains available. All new chunks are generated and validated before existing chunks are replaced in one database transaction. Failed generation leaves the previous vector records intact. No schema migration is needed. The current database supports only 384-dimensional embeddings, and incompatible or non-finite output fails explicitly. Replacing model weights under the same model name is not detected; use a distinct model name or forget and reindex the affected files.

This first implementation uses bounded keyword retrieval, not vector embeddings or model training. It is appropriate for a small personal text collection, not whole-drive knowledge. Synonyms and broad questions may miss relevant text. Be specific; a missing match does not prove the information is absent. The model is instructed to state its understanding, clarify ambiguous requirements, and check its answer. This is a prompt-based aid, not an independent factual verifier.

Supported files: UTF-8 `.txt` and `.md`, up to 16,000 bytes each; `.docx` up to 2,000,000 bytes with at most 16,000 UTF-8 bytes of extracted text. DOCX is read-only: main-body paragraphs and table text are extracted, without images, headers/footers, page layout, or OCR. Citations refer to extracted-text lines, not Word pages. Edit in Word and reindex. ZIP expansion is capped at 8 MB, document XML at 1 MB, entries at 1000, and XML depth at 128. External XML resources and DTDs are rejected. Empty, malformed, encrypted, or over-limit documents are skipped during folder indexing and return errors on direct read. Index limit: 100 files, 2,000 visited entries, folder depth 6. Listings show at most 200 supported entries. Hidden/system/credential/application-data paths, UNC paths, links and junctions are excluded. Files remain subject to Windows permissions. Permission to browse the computer does not cause automatic indexing of every drive. Legacy `.doc`, other Office formats, source-code edits and arbitrary binary files are not supported yet.

Persistent storage: `data/file-memory.json` under the application working directory (run the startup script from `D:\Jarvis\jarvis-ai`). It contains selected file paths, indexed text snapshots, hashes and explicit memory notes. It is ignored by Git and stored in plaintext locally, not encrypted. Retrieval rereads source files; deleted, inaccessible or changed files are not answered from obsolete snapshots. Re-index a folder to refresh the stored snapshots and discover new files. **Forget from index** removes its saved copy without deleting the original. Save blank memory notes to clear them. No implicit conversation profiling or model-weight updates occur.

Edits: open a supported file, type a change and choose **Review manual edit**. Or ask for an AI suggestion on files up to 600 UTF-8 bytes. Review the complete before/after text and choose **Apply reviewed edit**. Suggestions cannot execute actions. Both edit routes are proposals stored on the server; submitting a proposal does not write the source. Applying verifies the original SHA-256 hash, saves an original-text backup in `data/backups/<proposal-id>.txt`, then atomically replaces the file. If the source changed, reload it and make a new proposal. Proposals expire on restart or after newer proposals exceed the 20-item limit. Restore a backup by copying its content back through the reviewed editor. Backups remain until you remove them locally.

All routes require the existing bearer token. This grants the single local user supported-file access across the computer; keep it private and never expose the server beyond loopback. Path checks reduce accidental access but are not an OS sandbox against another malicious process changing filesystem links at the same time. Do not run multiple JARVIS instances against the same memory store.

API: `/api/v1/files/browse`, `/read`, `/memory`, `/index`, `/forget`, `/answer`, `/suggest`, `/propose`, `/apply`. Reads and index work run outside the HTTP event loop. Memory writes use a version check; file writes use the content hash. PostgreSQL/vector storage can replace this store later without retraining the chat model.
